## Overview

Some workloads cannot call an API for every address. If you are enriching billions of rows in a warehouse, running inside an air-gapped network, or working against a latency budget that leaves no room for a network round trip, a per-request lookup does not fit.

For those cases you can license Abstract's IP data as a database and run lookups locally, from a file you host yourself, with no rate limits and no per-request latency. How the file relates to the API is covered in [How the database compares to the API](#how-the-database-compares-to-the-api) below.

## Available databases

Three databases are available. You can license them individually or together.

| Database | What it answers |

## Delivery formats

Every database ships in two formats. Your license covers the database, so you can take either format, or both.

**MMDB** suits fast lookups by IP address in a running application: the format resolves an address to its **most specific** network in a single indexed read. **CSV** suits loading into a warehouse, a relational database, or a data pipeline, and inspecting the data directly. Nested CIDRs are valid in both formats; see [Overlapping networks](#overlapping-networks).

| Database | MMDB archive | CSV archive |
|---|---|---|
| IP to Geolocation | `abstract-ip-geolocation.tar.gz` | `abstract-ip-geolocation-csv.tar.gz` |
| IP to ASN | `abstract-ip-asn.tar.gz` | `abstract-ip-asn-csv.tar.gz` |
| IP to Security | `abstract-ip-security.tar.gz` | `abstract-ip-security-csv.tar.gz` |

Each archive contains three files: the database itself, a SHA-256 checksum of it, and a `README.md` describing that database.

Builds are reproducible. Two builds from identical inputs are byte-identical, so if you re-download an unchanged build you get the same checksum.

## Downloading the database

Once your organization is entitled to a database, you request a download link from the API and then fetch the archive from that link.

```
GET https://api.abstractapi.com/v1/database/download/
  ? api_key  = YOUR_API_KEY
  & database = ip-geolocation   (optional)
  & format   = mmdb             (optional)
```

<ParamField query="api_key" type="String" required>
  An API key belonging to the organization that licensed the database. This is the same key you use for your IP Intelligence requests.
</ParamField>

<ParamField query="database" type="String">
  Which database to download: `ip-geolocation`, `ip-asn`, or `ip-security`. Defaults to `ip-geolocation`. Your organization must be entitled to the database you ask for.
</ParamField>

<ParamField query="format" type="String">
  Which delivery format to download: `mmdb` or `csv`. Defaults to `mmdb`. Your license covers every format of a database you are entitled to, so this parameter is free to change.
</ParamField>

<ParamField query="response" type="String">
  Set to `json` to receive the download link in a JSON body instead of being redirected to it. Any other value, or omitting the parameter, returns the redirect.
</ParamField>

### Response

A successful request answers **302 Found** with an empty body. The `Location` header carries a temporary link to the archive, so a client that follows redirects downloads the file in one step.

```
HTTP/1.1 302 Found
Location: https://<storage-host>/abstract-ip-geolocation.tar.gz?AWSAccessKeyId=...&Signature=...&Expires=...
Cache-Control: no-store
Content-Length: 0
```

The link in `Location` is time-limited and is a bearer credential: anyone holding it can download your file until it expires. Do not store it or script against it. Point your tooling at the endpoint above and let it redirect each time, so the link you keep is always ours and never the storage one.

### Getting the link as JSON

If you need the expiry rather than the file, add `response=json` and the endpoint answers **200** with a body instead of redirecting:

```json
{
  "url": "https://<storage-host>/abstract-ip-geolocation.tar.gz?AWSAccessKeyId=...&Signature=...&Expires=...",
  "expires_in": 604800
}
```

<ResponseField name="url" type="String">
  The same time-limited link the redirect would have sent you to. Treat it as a secret.
</ResponseField>

<ResponseField name="expires_in" type="Integer">
  How long the link stays valid, in seconds. The maximum is 604800, which is 7 days.
</ResponseField>

### A complete download

One command. `-L` is required, because the endpoint answers with a redirect and curl does not follow redirects by default:

```bash
curl -L -o abstract-ip-geolocation.tar.gz \
  "https://api.abstractapi.com/v1/database/download/?api_key=YOUR_API_KEY&database=ip-geolocation&format=mmdb"
```

### Response and error codes

| Code | Type | Details |
| --- | --- | --- |
| 302 | Found | The default success response. `Location` carries the download link. |
| 200 | OK | Returned only with `response=json`. The body carries the link. |
| 400 | Bad request | The `api_key` parameter is missing. |
| 403 | Forbidden | Four distinct causes share this one response, so it does not tell you which applied: an unknown, disabled, or revoked key; an organization without an active entitlement for the database; a `database` value that is not in the catalog; a `format` value that is not in the catalog. If you are entitled and still get a 403, check those two parameters for a typo before contacting support. |
| 503 | Service unavailable | Downloads are temporarily unavailable. Retry, and contact support if it persists. |

Note that a rejected key answers 403 here, while Abstract's other APIs answer 401.

## Verifying your download

These files are large, and a download that is truncated or corrupted in transit will still open and still return answers, just wrong ones for part of the address space. The checksum separates a broken download from a genuine data question, before you spend time debugging the wrong thing.

Each archive ships a `.sha256` file next to the database. It holds a fingerprint of the exact bytes the build produced. Comparing it against the file you received confirms the two match.

Extract into a directory of its own. Every archive carries a `README.md` at its root, so extracting two of them into the same folder overwrites one with the other:

```bash
mkdir -p abstract-ip-geolocation
tar -xzf abstract-ip-geolocation.tar.gz -C abstract-ip-geolocation
cd abstract-ip-geolocation
```

Then verify:

```bash
sha256sum -c abstract-ip-geolocation.mmdb.sha256   # Linux
shasum -a 256 -c abstract-ip-geolocation.mmdb.sha256   # macOS
```

An intact download prints:

```
abstract-ip-geolocation.mmdb: OK
```

Anything else means the file did not arrive as it was built. Download it again and verify once more before you look at the data itself.

## Reading the MMDB

The `.mmdb` files use the standard MMDB binary format with a flat, string-valued record per network. Open one with any MMDB reader library for your language and use the reader's generic lookup by IP address:

```python
import maxminddb

reader = maxminddb.open_database("abstract-ip-geolocation.mmdb")
reader.get("73.158.0.5")
# {'country': 'United States', 'country_code': 'US', 'country_is_eu': 'False',
#  'continent': 'North America', 'continent_code': 'NA',
#  'region': 'California', 'region_iso_code': 'US-CA',
#  'city': 'Berkeley', 'city_geoname_id': '5327684', 'postal_code': '94707',
#  'latitude': '37.8922', 'longitude': '-122.2729',
#  'timezone_name': 'America/Los_Angeles'}
```

A record carries only the fields that have a value, so the number of keys varies by address. The lookup above returns 13 of the 16; a lookup on an address with no city or postal code returns fewer.

The record layout is flat key/value. Reader helper classes that expect a nested layout do not apply to these files, so use the generic lookup rather than a typed convenience method.

`get()` already applies [longest-prefix match](#overlapping-networks): it returns the most specific network that contains the address, so an MMDB lookup never yields two locations.

### Reading the CSV

The CSV carries the same data with one header row and one row per network:

```
network,country,country_code,country_geoname_id,country_is_eu,continent,continent_code,continent_geoname_id,region,region_iso_code,region_geoname_id,city,city_geoname_id,postal_code,latitude,longitude,timezone_name
1.0.1.0/24,China,CN,1814991,False,Asia,AS,,,,,,,,34.7732,113.7220,Asia/Shanghai
1.0.112.0/20,Japan,JP,,False,Asia,AS,,Shimane,JP-32,,Matsue,1857550,690-0801,35.4785,133.0489,Asia/Tokyo
```

Parse it with a real CSV reader, not by splitting on commas. Place names containing commas are quoted per RFC 4180, and thousands of rows in the geolocation file are affected.

A CSV query that tests "does this IP fall in the row's network?" can return more than one row. That is expected. See [Overlapping networks](#overlapping-networks) for the rule that picks the answer.

## Overlapping networks

A more-specific CIDR can sit inside a broader one, and both records ship. The inner block is a more precise answer for a subset of the outer block, not a duplicate.

```
172.58.64.0/22   Oklahoma     (172.58.64.0 – 172.58.67.255)
172.58.64.0/21   California   (172.58.64.0 – 172.58.71.255)
```

CIDR blocks never overlap only in part: two prefixes are either disjoint, or one contains the other. Lookups use **longest-prefix match**, the same rule IP routing uses. Among the records whose network contains the IP, the one with the longest prefix is the answer. `/22` beats `/21`.

| Address | Matching rows | Answer |
|---|---|---|
| `172.58.64.10` | `/22` Oklahoma and `/21` California | Oklahoma |
| `172.58.68.10` | `/21` California only | California |

**MMDB.** The reader's `get()` applies this rule and returns one record. You do not have to resolve overlaps yourself.

**CSV.** A containment query can return every covering row. Keep the row with the largest prefix length. Do not pick at random, combine the two locations, or drop one row as a duplicate.

Python:

```python
import ipaddress

addr = ipaddress.ip_address("172.58.64.10")
matches = [
    row for row in rows
    if addr in ipaddress.ip_network(row["network"])
]
winner = max(matches, key=lambda r: ipaddress.ip_network(r["network"]).prefixlen)
```

PostgreSQL:

```sql
SELECT *
FROM geo
WHERE inet '172.58.64.10' <<= network::inet
ORDER BY masklen(network::inet) DESC
LIMIT 1;
```

This rule applies to all three databases. For IP to Security, the most specific row already carries the [union of enclosing flags](#schema-ip-to-security), so keeping that row is also how you get the complete flag set.

## Conventions

These hold across every database and both formats:

- **All values are strings**, including `latitude`, `longitude`, and `asn`.
- **A field with no value is absent** from the MMDB record and **empty** in the CSV row. There are no null sentinels, so check for absence rather than comparing against a placeholder.
- **In the MMDB, the security flags only ever appear as `"True"`.** A false flag is absent from the record rather than set to `"False"`, so testing `record.get("is_vpn") == "False"` never matches. Test for presence instead. The security CSV is different: every row carries all seven flag columns with an explicit `"True"` or `"False"`, and a non-empty `"False"` is truthy in most languages, so compare the value rather than testing the column for emptiness. In the geolocation database, `country_is_eu` likewise carries a literal `"False"`.
- **Place names are in English.** Localized name variants are not available in this version.
- **Private, reserved, and multicast ranges are filtered out** at build time. A lookup against one returns nothing rather than a partial answer.
- **Nested CIDRs are valid.** A more-specific block inside a broader one is a hole with its own answer, not a duplicate. MMDB lookups resolve this automatically; CSV lookups must keep the most specific matching row. See [Overlapping networks](#overlapping-networks).

## Schema: IP to Geolocation

One record per network block, IPv4 and IPv6. The rows below are in the order the columns appear in the CSV, so you can map them positionally. In the MMDB, `network` is the key you look up rather than a field inside the record, so a lookup returns up to the other 16 fields.

| Field | Description |
|---|---|
| `network` | CIDR block the record applies to |
| `country` | Country name, in English |
| `country_code` | ISO 3166-1 alpha-2 country code |
| `country_geoname_id` | GeoNames identifier of the country |
| `country_is_eu` | Whether the country is an EU member |
| `continent` | Continent name, in English |
| `continent_code` | Two-letter continent code |
| `continent_geoname_id` | GeoNames identifier of the continent |
| `region` | Region or subdivision name, in English |
| `region_iso_code` | ISO 3166-2 subdivision code |
| `region_geoname_id` | GeoNames identifier of the region |
| `city` | City name, in English |
| `city_geoname_id` | GeoNames identifier of the city |
| `postal_code` | Postal code |
| `latitude` | Decimal latitude of the location |
| `longitude` | Decimal longitude of the location |
| `timezone_name` | IANA time zone name, for example `America/Los_Angeles` |

Country-level fields resolve for effectively every network. Everything finer is optional: not every routed network has a publishable region, city, or postal code. Read every field as optional and fall back to the country when the finer ones are missing.

`region_iso_code` carries the full ISO 3166-2 code, country prefix included (`US-CA`), on every row that has one.

## Schema: IP to ASN

One record per routed network block, IPv4 and IPv6, built by Abstract from public BGP routing data.

| Field | Description |
|---|---|
| `network` | CIDR block the record applies to |
| `asn` | Autonomous system number announcing the range |
| `autonomous_system_organization` | Organization operating the ASN |
| `asn_country` | Country the ASN is registered in, as an ISO 3166-1 alpha-2 code |

## Schema: IP to Security

One record per network carrying at least one flag. A network absent from this database carries none of them.

| Field | Description |
|---|---|
| `network` | CIDR block the record applies to |
| `is_vpn` | The range is used by a VPN service |
| `is_proxy` | The range is used as a proxy |
| `is_tor` | The range is part of the Tor network |
| `is_hosting` | The range belongs to a hosting or cloud provider |
| `is_relay` | The range is used as a relay service |
| `is_mobile` | The range belongs to a mobile network |
| `is_abuse` | The range has been flagged for abusive behavior |

These are the same seven signals the `security` object returns in an IP Intelligence response. The two formats encode a false flag differently: the MMDB record holds just the flags that apply, so a network flagged only as hosting returns one key, not seven, while the CSV carries all seven columns on every row with an explicit `"True"` or `"False"`.

A more-specific network inside a larger flagged range carries the **union** of its own flags and the enclosing range's. Nested CIDRs are valid; keep the [most specific covering row](#overlapping-networks), which already includes the enclosing flags.

## Refresh cadence

| Database | Rebuilt |
|---|---|
| IP to Geolocation | Weekly |
| IP to ASN | Weekly |
| IP to Security | Daily |

Security data moves fastest, so it rebuilds daily. VPN and proxy ranges change from one day to the next, and a security snapshot ages badly.

Geolocation and ASN change more slowly. In practice builds often land sooner, but weekly is the schedule to design against.

## How the database compares to the API

The database and the API are built to answer the same question, and for the overwhelming majority of addresses they return the same answer. Three differences are worth knowing before you choose, and they matter most if you plan to join the two.

**Some of what the API returns is not in the file.** Fields IP Intelligence computes at request time are absent: `currency`, `flag`, and the local time and DST state inside `timezone`. You get `timezone_name` and derive the clock yourself. Three more are absent because they are not part of a geolocation record: the whole `company` object, the whole `domains` object, and `asn.domain` and `asn.type`. ASN number and organization are available, in the separate IP to ASN database.

**Field names differ between the two.** If you key anything on field names, map them:

| API field | Database field |
|---|---|
| `location.is_country_eu` | `country_is_eu` |
| `timezone.name` | `timezone_name` |
| `asn.name` | `autonomous_system_organization` (IP to ASN) |
| `asn.asn` | `asn` (IP to ASN) |
| not returned | `asn_country` (IP to ASN) |

`region_iso_code` also differs in format, not just in name. The database returns the full ISO 3166-2 code (`US-CA`), while the API returns the bare subdivision (`CA`). Strip the prefix before joining on it.

**A small share of addresses can differ.** The API consults live sources on some requests that a static file cannot reproduce. Where that happens, the database answers from its own build instead. The share is small, and if you need it quantified for your evaluation, ask our sales team for the current figure.

If your workload needs the runtime-derived fields, or you need the freshest possible answer on individual addresses, use the API. If you need volume, local latency, or offline operation, use the database. You can also run both: the database for bulk enrichment, the API on the request path.
